# 2026-08-21 — KLE에서 DXF를 생성해 배열 원천을 하나로 만든다 (part 1/2)

> fg-next all 드라이브가 자동 스킵한 회고를 나중에 일괄 승급한 것이다 (2026-08-21).

## 계획 대비 실제

- 계획대로 된 것: 슬라이스 5개 전부 완료, DoD 9항목 전부 통과. TDD 가 실제로 작동했다 —
  회귀 테스트를 먼저 쓰고 `gen_dxf` 부재로 실패(exit 1)를 확인한 뒤 구현해 통과시켰다.
  **그릴링에서 코드 실측으로 확정한 생성 규칙 6항을 한 항목도 수정할 필요가 없었다.**
- 이탈:
  1. 공용 DXF 파서 `tools/dxf.py` 를 추가했다 (계획은 2개 파일, 실제 3개).
  2. DoD 8이 지목한 3개 사이트 중 하나(README 의 낡은 갈래 언급)가 **실재하지 않았다.**

## 배운 것

- 다음에 다르게 할 것:
  1. **DoD 에 사이트를 열거할 때 그 사이트가 실제로 있는지 먼저 확인한다.**
     "낡은 갈래 3개(스크립트 2곳 + README 의 해당 언급)에 주석" 이라 썼지만 README 에는
     `create_keyboard_plates.py`·`create_techdraw_sheets.py`·`keyboard_switch_plates.FCStd`
     를 언급하는 곳이 아예 없었다. `grep -n 'create_keyboard_plates' README.md` 한 줄이면
     그릴링 시점에 알았다. **없는 사이트를 세면 통과 조건이 애매해진다** — 있는 사이트를
     빠뜨리는 것(#9 의 수량 누락)과 반대 방향의 같은 실수다.
  2. **데이터 형식을 다루는 작업은 파서/직렬화기가 계획보다 파일 하나를 더 요구한다.**
     지난 작업의 `tools/kle.py` 와 이번 `tools/dxf.py` 가 같은 패턴이다. 다음에 형식 변환
     작업을 계획할 때는 파서 모듈을 슬라이스에 처음부터 넣는다. 이번엔 DoD 3 자체가
     "생성물을 `create_keyboard_parametric.py` 와 **같은 파서**로 되읽어 검사한다"고 요구해
     읽기 파서가 필수였으므로, 계획 단계에서 도출 가능한 요구였다.
  3. **유지할 것 — 그릴링에서 측정한 것이 실행에서 손댈 일을 없앴다.** 생성 규칙(1u=19.05mm,
     오프셋, 슬롯 ±11.9/−0.65/3.3×14.201, 외곽선 +2.5mm)을 전부 코드 실측으로 확정해
     플랜에 적어 뒀기 때문에, 구현이 그 표를 옮겨 적는 일이 됐다. 추측으로 적었다면
     구현 중에 값마다 되돌아왔을 것이다.
  4. **유지할 것 — 원본 대조 회귀 테스트를 택한 판단이 옳았다.** 왕복 검증(생성한 5행 DXF 를
     5행 KLE 와 대조)으로는 규칙 자체의 오류를 못 잡는다는 그릴링 때의 논거가 실제로
     성립했다. 통과 결과가 "규칙이 원본을 재현한다"는 증명이 됐다.

## 확인된 사실

- 회귀 테스트 실측: 좌 스위치 37개 편차 0.0006mm · 슬롯 4개 0.0004mm, 우 스위치 51개
  0.0006mm · 슬롯 6개 0.0005mm. 허용치 0.01mm 의 1/16.
- 5행 DXF 행 y중심 `[10.0, 29.0, 48.1, 67.1, 86.2]` — KLE 총 높이 기반 y 반전이 오프셋
  보정 없이 자연히 맞아떨어졌다.
- `tools/gen_dxf.py`·`tools/gen_keylayout.py` 모두 멱등이다. 재실행해도 README 의 수동
  주석과 절차 단락이 보존된다.
